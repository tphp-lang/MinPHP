# TinyPHP 综合分析报告

> 2026-09-09 · 基线：commit 004（e7c2df0）· 全部数据为当日实测
> 环境：Windows 11 x64 · PHP 8.5.1 NTS VC++ x64（编译器宿主 + 对照）· 自带 TCC（后端）

## 一、总评

一个**工程成熟度远超其阶段数字**的研究型 AOT 编译器：1.2 万行 PHP 实现了
「强类型 PHP 子集 → 人类可读 C → 原生 exe」的完整流水线，62 个测试用例全绿，
语法层已覆盖类/接口/枚举/闭包/命名空间/错误处理等 PHP 现代特性的核心部分。
计算性能对 PHP 8.5 呈碾压态（8.7–12.9x），产物 16KB 零依赖可交叉四平台。
当前三大短板：**无关联数组（map）**、**字符串累加性能差 35 倍**、
**除零/栈溢出裸崩溃**——分别卡住表达力、性能、可用性三条路。

## 二、语法维度

**设计立场清晰**：表面 PHP（`$` 变量 / `->` / `foreach as` / `.` 拼接 / heredoc），
内核 C（静态类型、int 整除、严格 bool 条件、值/指针二分）。这个立场执行得很彻底，
`doc/grammar.md` 的 EBNF 与实现一致。

### 已覆盖（有完整语义与测试）

| 类别 | 内容 |
|---|---|
| 类型 | int/float/bool/string/null/callable/void、array\<T\>、类/接口、c.* 别名 |
| 面向对象 | 单继承 + 多接口、public/private/protected、static、self::/parent::、__construct、self 返回类型链式 |
| 枚举类 | PHP 8.1 语义（case 单例、backed value、方法、接口、from/tryFrom/cases） |
| 函数式 | 闭包（fn 箭头 + function+use）、&引用捕获（堆盒子） |
| 错误处理 | `throw <string>` 上浮 + `调用 or {}` 捕获（err 只读），全程无签名标注 |
| 管道 | `\|>` 脱糖 + `...` 占位符（任意参数位），零运行时开销 |
| 组织 | namespace 多层名、use 分组/as、多文件合并单 TU、平台条件编译 #if |
| 互操作 | phpc：#include/#flag/#struct/#if、c-> 直连、#[export] C ABI 导出 |

### 短板（按影响排序）

1. **无 map/关联数组**——`array<T>` 是纯列表。现实程序一半以上的场景
   （查表、计数、JSON 结构）没有原生表达。这是与"实用语言"最大的差距。
2. **无 instanceof / 运行时类型判断**——接口变量拿到手后无法安全还原具体类型
   （itab 里存了实现类，机器层面可以做，语法层缺）。
3. **内置函数仅 6 个**（len/var_dump/c_str/php_str/php_str_ref/cbuf/c_own）。
   没有 strlen/strpos/substr/sprintf/array_*——连字符串切片都要手写循环。
4. 无 trait/abstract/final/匿名类/解构/spread/引用传参（`&$`）——均为刻意取舍，
   文档已声明，属设计而非缺失；但 `final` 与 `abstract` 建议进路线图（成本低）。

## 三、性能维度（实测）

### 运行性能（净计算时间，8 次平均差分法，已消除进程启动噪声）

> 2026-09-09 更新：已加入除零/取模零检查与递归深度保护（见 §四·安全开销），
> 下表为含安全插桩的最新数据。

| 基准 | 工作量 | TinyPHP (TCC) | PHP 8.5.1 | 倍率 |
|---|---|---|---|---|
| 递归 fib | 1140 万次调用 | ~60ms | ~416ms | **6.9x** |
| 试除素数 | 100 万数 | ~113ms | ~1189ms | **10.5x** |
| 虚方法分发 | 360 万次 vtable 调用 | ~103ms | ~136ms | 1.3x |
| 数组读写 | push+遍历+下标 100 万次 | ~21ms | ~32ms | 1.5x |
| 字符串累加 | 4 万次 `.` 拼接（O(n²)） | ~715ms | ~24ms | **0.03x** |

五个基准的输出双端逐字节一致。

- **整数/循环/递归碾压**（6.9–10.5x）：TCC 朴素代码在简单整数场景即为
  gcc -O0 水平，对 PHP VM 是数量级优势。
- **虚分发 1.3x**：单态化 vtable 每槽一次间接调用；小方法体的深度保护
  插桩占比高（见 §四·安全开销），无保护时为 2.3x。
- **字符串累加是唯一重灾区**：`$s = $s . "ab"` 每次全量拷贝到池新块且不回收，
  O(n²) 下 PHP（concat 自适应扩容 + 引用计数）反超 **35 倍**。
  正解工具已落地：**`implode(sep, parts)`**（2026-09-09）——4 万段拼接 5ms
  （同规模 O(n²) 拼接 709ms，约 140 倍）。根本性优化（原地 append）需要
  String 引用计数 + malloc 分配器，属内存模型 v0.3 重构。
- **数组 1.5x**：连续内存列表本可更快（预计 5x+），当前差在
  push 的 grow 路径与 foreach 的 ref/unref 插桩开销。

### 安全开销（除零检查 + 递归深度保护，2026-09-09 实测）

| 基准 | 无保护 | 函数版插桩 | 宏展开插桩 | 结论 |
|---|---|---|---|---|
| fib（重递归） | 48ms | 87ms (+81%) | 60ms (+25%) | enter/leave 必须**宏展开**——TCC 不内联 static 函数，调用形态开销翻倍 |
| primes（含 % 检查） | 92ms | 120ms | 113ms (+22%) | 每次非常量右值除/模插一个语句表达式（求值入 __d → cmp → 除） |
| poly（小方法体） | 60ms | 105ms | 103ms (+70%) | `return 2;` 这类 2 指令函数体上插桩占比天然高 |

后续优化项：调用图分析——仅对"可直接/间接到达自身"的函数插深度保护，
非递归函数（如 poly 里的 speak）零开销。

### 编译性能

| 指标 | 数值 |
|---|---|
| 端到端编译（含编译器 PHP 启动 + TCC 链接） | 0.64–0.76s |
| 产物体积 | **16 KB**（零依赖，含 RC/dtor/panic/echo） |
| 产物启动 | 数十 ms 级（此前 276ms 读数含 exec 框架噪声，非 exe 本身） |
| 交叉目标 | windows x86_64/i386、linux x86_64/arm64（musl 静态 ELF） |

## 四、实用程度

### 现在就能干的事

- 算法/数据结构实现与教学（语法完整、错误消息带源码定位、有 62 用例测试架）
- 纯计算 CLI 小工具（fib/素数/解析器级别的活，产物 16KB 直接分发）
- C 库绑定胶水：phpc 直连成熟 C 库，#[export] 反向导出 C ABI ——
  "PHP 语法写动态库给其他语言调用"这个定位目前没有竞品

### 干不了的事（按痛感排序）

1. **任何需要标准库的程序**：文件 IO、网络、JSON、日期、正则、数学函数——
   语言级一个都没有，全要 `#include` + `c->` 手写 C 桥。数学函数尤其可惜：
   `sqrt/pow` 只要预插 `<math.h>` 就白送。
2. **查表型程序**：没有 map，统计词频这类第一课程序都写不出来。
3. **大型项目组织**：无包管理/无 import 语义/单 TU 合并——单项目可接受，
   多项目协作缺基础设施。
4. **除零/栈溢出裸崩溃**（P0）：`1/0` 直接 `0xC0000094` 无任何输出——
   对"给 PHP 程序员的 AOT 语言"这个定位是可用性硬伤。

### 部署面（强项）

TCC 随项目分发、musl 静态 ELF 不依赖目标 libc、单文件 exe、
`--emit-c` 可把生成的 C 拿去任何 C 工具链继续用——
"人类可读的 C 作为中间产物"这个设计在部署维度是真优势。

## 五、架构维度

### 模块结构（12,066 行编译器 + 863 行运行时头文件）

```
Scanner   676 行   手写词法（含 heredoc/插值/#token）
Parser   1958 行   递归下降，Expr/Stmt/Decl 三 trait 水平切分
Checker  3070 行   两遍式：收集符号 → 全量类型标注（Gen 零推断）
Gen      3401 行   分节输出（head→main 八节）+ #line 回源 + RC 插桩
Table     750 行   类型编码 + 全局符号表（单一事实来源）
Ast      1253 行   62 个节点类，每节点一文件
其他      953 行   Pref/Builder/Errors/Token/Type
runtime   863 行   纯头文件：String(SSO+池)/Array/对象头/RC/err/cmem
```

### 设计亮点

- **单一事实来源**执行得好：Type 编码 + Table 符号表贯通六阶段，
  Gen 是纯消费者——加新语言特性时改 Checker+Gen 两处即可，这个纪律在
  枚举类/闭包/管道这类复杂特性上经住了验证。
- **trait 水平切分**让三巨头（Parser/Checker/Gen）各自保持 3-4 个 1000 行内文件，
  比单文件巨石可维护得多。
- **runtime 纯头文件 + TCC 单 pass**：无链接期 ABI 问题，--emit-c 产物自包含。
- 测试架（62 用例 + 期望输出 + mem-stats 断言）与文档（1006 行六篇）
  是同类个人项目里罕见的完整度。

### 技术债

| 项 | 严重度 | 说明 |
|---|---|---|
| ~~除零/栈溢出裸崩溃~~ | ✅ 已修复（2026-09-09） | 除法/取模零检查 + 递归深度宏保护，新增 36/41 用例；开销见 §四·安全开销 |
| 引用循环泄漏 | P1 | 文档化已知限制；直接自引用已编译期拒绝 |
| 字符串累加 O(n²) | P1 | 唯一性能重灾区，修法明确 |
| `#line` 行号偏移 | P2 | helper 节插入导致警告回源错位（39 用例报 178 实际 106） |
| Table 反查 O(n) | P3 | displayName/isIntLike 用 array_search，规模大后需加缓存 |
| Gen/Checker 最大文件 1317 行 | P3 | 尚可，再增长建议拆分 |

### 可扩展性判断

加新语法的成本结构健康：词法（Scanner 集中）→ AST（新增一个节点类）→
Parser（对应 trait 一段）→ Checker（标注）→ Gen（输出）。
管道 `|>`、枚举类、闭包引用捕获三个复杂特性都是按这个路径加的且质量稳定——
架构对演进的友好度是本项目最强的部分。

## 六、结论与建议顺序

TinyPHP 已完成「语言能自举使用、测试全绿、性能数量级优势」的第一阶段。
下一阶段的优先级建议：

1. ~~P0 运行时安全~~ ✅（2026-09-09）：除零/取模 panic 化 + 递归深度宏保护，
   新增 36/41 用例；安全开销见 §四
2. ~~字符串正解工具~~ ✅（2026-09-09）：内置 implode（4 万段 5ms，约 140 倍于
   O(n²) 拼接）；根本性原地 append 待内存模型 v0.3（String RC + malloc）
3. ~~map 类型~~ ✅（2026-09-09）：`map<K,V>` 落地（K 限 int/string，V 限标量与
   string；哈希表链地址 + FNV-1a；下标读写/len/array_keys；缺失键 panic；
   遍历用 array_keys + 下标读，哈希无序不保证键序）。第一版边界：map 不作
   字段/数组元素/嵌套（Checker 明确拒绝），=> 字面量语法与堆值 V 待后续
4. ~~调用图插桩收窄~~ ✅（2026-09-09）：Checker 记调用边（方法动态分发按
   类+全部子类、接口按全部实现类、闭包调用强制保护）→ 环检测 → 仅自可达
   函数插深度保护；poly 生成代码插桩 4→0，fib 保护保留
5. ~~map 的 => 字面量~~ ✅（2026-09-09）：全键形式推导 map<K,V> + 目标
   K/V 逐对校验回填
5. （远期）instanceof / final / abstract / 包管理
